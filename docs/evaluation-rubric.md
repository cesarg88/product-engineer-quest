# Evaluation Rubric

## Purpose

This rubric exists to evaluate evidence of competence without turning PEQ into a scoring system.

The goal is to make progress visible while keeping the system lightweight.

---

## Deliverable vs Evidence of Competence

A deliverable is the artifact that must exist.

Evidence of competence is what the artifact demonstrates.

A file created in the repository is not enough to prove learning.

The content should show that a specific capability is improving.

Example:

- Deliverable: `journal/product-analyses/01-fever-favorites.md`
- Evidence of competence: the analysis distinguishes problem from solution, defines a hypothesis, chooses a useful metric, identifies risk, and explains trade-offs.

---

## Levels

Use only these three levels.

| Level | Meaning |
| --- | --- |
| Developing | The capability is present but incomplete, shallow, or still dependent on guidance. |
| Competent | The capability is demonstrated clearly in this exercise. |
| Independent | The capability is demonstrated clearly and could likely be applied without guidance in a new context. |

Do not add numeric scores.

Do not add XP.

Do not add badges.

Do not automate this yet.

---

## How to Use the Rubric

Apply the rubric to specific capabilities inside each exercise.

Do not evaluate a full milestone with one generic level.

Example:

| Capability | Level | Notes |
| --- | --- | --- |
| Define the user problem | Competent | The analysis identifies rediscovery friction clearly. |
| Build a product hypothesis | Developing | The hypothesis exists but could be more falsifiable. |
| Choose useful metrics | Developing | Metrics are relevant but need stronger connection to business value. |
| Identify trade-offs | Competent | Several product and execution trade-offs are visible. |

## Rule

The rubric should support learning, not judgment.

If the rubric starts to feel like bureaucracy, simplify it.
